6. 工厂机制架构变更 (Architecture Changes)

从硬编码与松散生成走向表驱动与严格交叉校验
1. update / constrain / evaluate 全面改为表驱动
淘汰了过去散落在生成逻辑里的零碎规则，将多样性源头收敛到结构化种子表（UPDATE_ROWS、CONSTRAIN_ROWS、EVALUATE_ROWS）。生成器仅负责按种子抽样与环境组装，不动态拼接变异字段。
2. query 坚持手写自然口语 + validator 交叉核对门禁
题目 query 文本坚持人工手写以保留真实的口语化表达多样性，杜绝模板感；同时在 validator.py 中新增严格的交叉核对门禁（例如：检查 delta 数值是否在句子中出现、增减方向词与数值正负号一致、过敏原 tag 能在 query 中找到对应词汇），确保口语自然句与 oracle 终态严格等价。
3. constrain 确立两种独立的 oracle 契约
将过去模糊的拒答逻辑拆分为两类显式契约： condition（用户点名食物含有画像中的过敏原，拒绝生成计划，allow_empty_plan=False）与 conflict（用户提出物理/生理不可满足的极端指标如 100 kcal 内含 100g 蛋白质，allow_empty_plan=True）。
4. evaluate 种子表存储 margin 而非硬编码营养窗口
EVALUATE_ROWS 仅持久化食物名称、口语分量短语与 margin 的绝对值（默认 kcal ±150、protein ±15）。题目物化时，由 live catalog 动态计算出精确克数与对应营养素窗口，彻底解除了与静态硬编码数字的耦合。

7. 已知缺陷与遗留问题 (Known Gaps)

实事求是记录，不粉饰、不回避
1. evaluate 家族严重滞后 (7 / 48)
当前 evaluate 仅完成 7 题（完成度 15%），是五个家族中进度最落后的一环。虽然工厂表结构已建立，但有效 candidate meal 组合仍待进一步扩充物化。
2. 本轮 36 条新增题目未经人工逐条审核
新增的 36 项题目全部通过了机器门禁校验（validator.py）与 LLM 自动化复核，但尚未由人类专家逐题通读核对。在最终进入 v1 冻结集前，仍需执行人工核准流程。
3. Catalog 中 14 个 0 kcal 微量蛋白条目的理论漏洞
USDA Catalog 中存在 14 个标称 0 kcal 但含有微量蛋白质的条目（实际都是脱因咖啡一类饮品，每 100 g 约 0.1 g 蛋白）。在理论上，一个无条数上限的解可以通过无限堆叠此类条目来满足极端苛刻的“低热量 + 高蛋白”窗口。该问题为 catalog 固有历史遗留，亦存在于 gold item 对应数据中，但当前已冻结的题目用例未受其实际干扰。
