# NutriEnv v1.0（内部 v2.5）构造效度裁决

> 裁决人：Claude Opus（深度终审）
> 对象：DeepSeek-V4-Flash 60.9%（78/128）与 GLM-5.3-flash 57.0%（73/128）在 `data/splits/nutrienv-gold.json` 上的真机轨迹；`src/nutrienv/harness/react.py` v0 手册；`src/nutrienv/bench/scorer.py`；FNDDS catalog-v2。
> 方法：不采信用户转述中的题干/克数，逐项回读冻结 split、catalog `portions`、两条 `reports/benchmark_ark_*_v1.0.json` 轨迹。
> 版本纪律：已发布 split 不就地改金标（ADR 0025）。本裁决区分「手册缺陷（可出新 harness 版本）」与「题目缺陷（出下一版 split + errata）」。

---

## 〇、结论先行

四项全部成立，但补救位置不同。总原则：

**手册只描述世界物理与工具信封；题干必须使 Oracle 对合格读者可唯一恢复；判分器继续坚持 `Pass ⇔ end state == Oracle`，不靠放松判分去掩盖出题错误。**

| 议题 | 裁决 | 落地位置 |
|---|---|---|
| 1. 业务小抄指引 | **删除套路教唆，保留 API / 物理 / 交卷规则** | 新 harness 版本（建议 `react-v2`）；冻结现 `react-v0` 以便复现 60.9 / 57.0 |
| 2. 歧义 Log 题 | **禁止无条件整桶删除；按可唯一恢复性分流：修 query / 改绑 NFS / 删题** | 下一版 Gold（v1.1）；本版出 errata |
| 3. Evaluate accept 时态 | **(a) 必须改咨询时态；(b) 禁止判分器解耦多记的账** | 下一版 Gold 改题干或改复合题；**不改 Scorer 铁律** |
| 4. `amend_meal` 漏注册 | **必须补进 Available ops，只写信封与物理** | 与议题一并进入 `react-v2` |

用户说 GLM 在 Evaluate 上被冤死 5 道：轨迹实为 **4 道 `log_miss`（1003 / 1005 / 1006 / 1007）**，均已给出正确 `verdict=accept` 且餐盘与金标一致；1008 是 `wrong_goal`（克数乱编 + 多记），不算同一类冤案。定性成立，计数订正为 4。

## 一、议题一：系统 Prompt 去小抄化

### 1.1 现状不是「只有工具列表」

`react.py:51` 现行 v0 手册在「How an episode is graded」里写了具体做题套路：

> ate then "what to eat next" is log_meal … then submit_plan …; allergy change then dinner ask is update_profile then submit_plan; ate then "is this okay?" is log_meal then verdict=accept.

这不是工具 schema。这是把 Composite / Evaluate 的出题模板翻译成标准答案路径。`tests/test_react.py` 还把它钉成了回归（`log_meal then verdict=accept`），所以这是有意写入，不是残留。

ADR 0021 / 0023 的阶段二定义是：受测手册只提供工具定义与简明交互协议，考核常识推理，禁止硬编码小抄。v0 对口语量词字典已经遵守（`test_react_v0_is_the_frozen_baseline_manual` 断言 `"portions" not in v0`），但对**意图路由**没有遵守。

### 1.2 轨迹上的构造性自伤

GLM 在 `adr25-eval-1003/1005/1006/1007` 上严格执行了这句话：用户说 "I ordered … Can you evaluate"，模型先 `log_meal` 再 `submit_plan(verdict=accept)`，餐盘 grams 与金标一致。金标 `oracle.ledger = s0`（空账）。Scorer 走全量 `ledger` 多重集相等 → `log_miss`。

这不是模型「太笨」，是**手册标准答案与 Evaluate 金标互相否定**。手册教「吃过 + 好不好 = 记账 + accept」；出题人用过去时写纯 Evaluate，又要求账本保持 S0。GLM 越听话越零分。DeepSeek 在 1005–1007 上同一死法。

### 1.3 裁决

**(a) 是。** 删除所有「听到句式 X 就调用工具链 Y」的套路。手册允许且只允许三类内容：

1. **工具信封**：op 名、必选/可选字段、取值约束（`grams > 0`、`verdict ∈ {accept,reject}`、reason 码表）。
2. **世界物理**：写入立刻生效；未知 `food_id` 不改世界；营养数字以 observation 为准；catalog 能量是每 100 g。
3. **交卷协议**：未提及字段保持 S0；多写请求必须都落到终态；`finish` 交卷；`submit_plan` 的 `verdict` / `items` / `reasons` 语义（这是该 op 的返回约定，不是某道题的解法）。

**(b) 是。** 多意图口语由 Agent 自己判断「这是已发生摄入还是咨询盘」。这正是基准要测的东西。把标准路径写进系统 prompt，测到的是依从性，不是意图识别。

明确保留、不要误删的：`submit_plan` 的 accept/reject 契约、过敏 reason 码、餐能量份额窗口、隐式 update 方向（不给步长）。那些是环境计分语言，不是「听到 ate 就 log」这种题型小抄。

v1 手册尾巴（`plate → portions.qns` 等）继续只作消融，不进发布 ReAct。ADR 0019 曾写「口语回写进 react.py」；**ADR 0021 已覆盖这条**，口语接地留在 `get_food` 观察里，不回写发布手册。

## 二、议题二：歧义题 —— 删还是修

### 2.1 分流标准（唯一恢复性）

一条 Gold 项合法，当且仅当：**只凭题干 + catalog 观察 + 已发布判分规则，合格标注员能把 `(food_id, grams)` 恢复到 Scorer 会判 Pass 的集合，且该集合不是「表上任意一行」这么宽。**

| 桶 | 条件 | 处置 |
|---|---|---|
| **A 修题干** | 金标本身合理，缺 1–3 个餐桌用词即可消歧；补词不违反 ADR 0022（不把 `NS as to fat` / `including carrots, broccoli, and/or dark-green leafy` 写进用户口语） | 改 query，不动 family |
| **B 改绑金标** | 题干更 entail 通用/NFS 款，金标绑了带修饰的孪生行 | 金标改 NFS 或无修饰款；query 可不动 |
| **C 删除/移出 Gold** | 消歧必须把 FNDDS 科研分类读出来；或同一题同时踩食物 ID 歧义与份量歧义，修完已不是原技能 | 移出 Gold，名额补新题 |
| **D 保留（模型错）** | 题干已给出可落地的量词或可唯一的食物，模型选了表外克数或错 ID | 不改题，不算假阴性 |

**否决**作为一般规则的「未说明分量 → 命中 portion 表任意一行即 Pass」。胡萝卜 `piece=5` / `qns=78` / `cup=155` 会一起过；5 g 当午餐在临床上不可接受。未给分量时，生成器默认 QNS 可以，但**必须把该默认变成题干里的可说量词**（`a serving` / `a plate`），不能把 QNS 当秘密答案。也不用放宽 ±15% 去覆盖 cup↔qns 的 20%+ 缺口——那是出题问题。

### 2.2 逐题

**`adr20-log-8205` — 桶 A（优先）/ C（消歧词写不出再删）**

- Query：*"I had a plate of beef and noodles with vegetables in tomato sauce."*
- 金标：`2706611` excluding @ 311 g（qns）
- 两模型：`2706610` including @ 311 g
- Catalog：including / excluding 克数相同；题干 "with vegetables" 对两行都真。including 是更自然的默认。
- **修**：口语排除，与 v2.3 对 5005 的补法对称（"no broccoli or extra greens"）。不要把 `excluding carrots, broccoli, and dark-green leafy` 写进题干。
- 若坚持考「排除深色叶菜」又写不出人话 → **删**。

**`adr20-log-5004` — 桶 A 或 B，不删**

- Query：*"… a handful of ready-to-eat flavored popcorn."*
- 金标：`2708237` **light** @ 28 g
- DeepSeek 碰巧中 light，Pass；GLM 记 `2708235` butter flavored @ 28 g，`log_miss`
- 题干没有 light。NFS 行是 `2708231`；butter 是「flavored」的常见默认。light 是未说出的修饰。
- **二选一**：query 加 "light"；或金标改绑 `2708231` NFS（handful→piece 28 g 仍成立）。汉堡那一半是好题，整题删除浪费。

**`adr20-log-5005` — 桶 D，保留；食物 ID 已在 v2.3 修好**

用户把本题说成「没给分量、金标锁 305 g」。冻结题干实际是：

> a plate of fish with noodles … — no broccoli or extra greens, just the fish and noodles.

食物 ID 已消歧到 `2706716`。DeepSeek 选对 ID，记 **cup 244 g**；金标是 **qns 305 g**。244/305≈80%，落在 ±15% 之外。`portions.py` 里 `plate → serving → qns`，生成器没错。

GLM 拆成鱼+面+酱三笔，是真错误，与克数窗口无关。

保留。代价：v0 观察里键名是 `qns` 不是 `serving`，模型可能不知道 qns 即默认份。这应在 **`food_view` 把 qns 同时暴露为 `serving`**（世界观察，不是手册小抄），而不是删题、也不是把 `plate→qns` 写回 prompt。

**`adr24-comp-8301` — 桶 A**

- *"I had tripe for lunch."* 无量词。金标 qns **85 g**。GLM **140 g = cup**（表内合法行）。DeepSeek 猜中 85，是运气。
- 85 与 140 都不是胡编。题干不可唯一恢复。
- **修**：加可说量词（"a serving of tripe" → QNS）。不删：后半段 activity→light 是有效 Update 复合。

**`adr24-comp-8303` — 桶 A**

- *"I had cooked fresh carrots for lunch."* 无量词。金标 qns **78 g**。
- GLM 记 **100 g**（**不在** portion 表：piece 5 / regular 60 / qns 78 / cup 155）。即便修了题干，100 g 仍应 Fail。DeepSeek 78 g 同样是猜中 QNS。
- 仍要修题干（"a serving of cooked carrots"），否则金标 78 是未公布默认。不删。

**`adr24-comp-9200` — 桶 D，保留**

用户把它与 8301/8303 并列，说成「I had chicken thigh、金标 75 g」。冻结题干是 **"I had a piece of grilled chicken thigh"**。`piece=75`，qns=80，cup=135。GLM 记 **100 g**（表外）。这是量词接地失败，不是出题霸权。

### 2.3 对「要不就删了」的直接回答

不要整桶删除 Log 不严谨题。Gold 纯洁度靠**可唯一恢复**，不靠「模型没过就扔题」。8301/8303/5004/8205 是出题债，优先一句人话消歧；只有科研孪生词条无法口语化时才删。5005 与 9200 留下。

## 三、议题三：Evaluate Accept 的时态与账本

### 3.1 事实

`adr25-eval-1001/1002/1004/1009/1010` 已是 *"Can you evaluate my planned lunch: …"*，两模型在这些上可以只 `submit_plan` 不过账。

`1003/1005/1006/1007/1008` 用过去时：*"I ordered"* / *"We went out"* / *"I got"*。金标仍 `ledger=s0`、`last_verdict=accept`。GLM 对 1003/1005–1007 的餐盘与 verdict 都对，死在多记。DeepSeek 1005–1007 同因。

家族定义：Standalone Evaluate 的餐是**候选盘**，不是已摄入事件。过去时摄入 + 评估 = Composite Log+Eval，必须有非空 `ledger_tail`。现在这五道是 Evaluate 的皮、Composite 的骨、空账的金标。

### 3.2 裁决

**(a) 是。** 纯 Evaluate 必须用咨询/规划时态，例如已用于 1001 的 *"Can you evaluate my planned lunch: …"*。禁止 *"I ordered / I ate / I had / I got / we went out"* 出现在 `family=evaluate` 且 `ledger=s0` 的题干里。

过去时要保留，就**改家族**：`compose_oracles(Log, Evaluate)`，`ledger_tail` 等于被评餐盘。名额从 Evaluate 挪到 Composite，或换新 Evaluate 补上。不允许继续挂 Evaluate 却按 Log+Eval 行为出题。

**(b) 否。禁止「核心是 Evaluate 则忽略一致的 log_meal」。**

理由：

- ADR 0002 / 0004：Pass 是终态等于 Oracle，不是「主要意图对了」。多记的行是多出来的状态。
- 放松 Evaluate 的 ledger 断言，等于把「未提及字段保持 S0」变成软约束，Composite 与 Evaluate 的边界消失。
- 临床上「评估顺手记账」合理，所以过去时题应改成 Log+Eval，而不是让 Scorer 装没看见。
- 假阴性在出题，不在判分。用判分器擦屁股会把下一轮假阴性变成不可审计的特例。

`submit_plan` 的餐盘与 `log_meal` 的账本在 Env 里是两条状态。Evaluate 金标查的是前者；多写后者就是多写。

## 四、议题四：`amend_meal` 手册文案

### 4.1 缺陷

Env 已实现 `amend_meal {index, grams, food_id?, eaten_at?}`（ADR 0026）。v0 手册 Available ops 未列出。`adr26-log-1307` 题干甚至用了英语动词 *amend*，两模型仍无法发现该 op：

- DeepSeek：`log_meal(grams=-60)` → schema 拒绝 → 超时。
- GLM：`log_meal(60)` 追加、`log_meal(-120)`、`delete_meal`、`log_meal(replace=true)`、把 observation 当 action 回放。全程 0 次 `amend_meal`。

在封闭 op 表里，未列出的动作等于不存在。这不是能力题，是**环境说明书漏页**。该题在发布协议下不可解。

### 4.2 规范文案（进 Available ops，不是进「做题提示」）

只允许下面这一档。不要写「用户说记多了就 amend」。

```
- amend_meal {index, grams, food_id?, eaten_at?}
```

在物理/信封段（与 `log_meal without eaten_at is stamped "now"` 同类）加一句：

```
- amend_meal overwrites ledger[index] in place. grams must be > 0. Omitted food_id and eaten_at stay. It does not append a row and does not delete a row. index is an integer into the current ledger from get_ledger.
```

禁止：

- 「日记记错了请调用 amend_meal」
- 教 `index=0` 对白米饭
- 暗示存在 `delete_meal` 或负克数冲销（物理上不存在，写了就是反向小抄）

删除议题一的套路句后，v0 400 词上限有空间容纳这两行。

## 五、落地顺序与版本

1. **立刻 errata（本版 `nutrienv-gold` / v2.5 不改字节）**  
   公布：手册含意图小抄；Evaluate 1003/1005–1008 时态与空账冲突；1307 缺 op 说明；8205/5004/8301/8303 不满足唯一恢复。60.9% / 57.0% 仅在 `react-v0` + 当前 split 哈希下可复现。

2. **`react-v2`（手册，独立于 split）**  
   删 `:51` 三条套路；注册 `amend_meal`；测试改为断言「无 ate-then 句式、有 amend_meal 信封」。保留 `react-v0` 复现旧榜。发布榜切换到 v2 后重跑，不回头改旧 JSON 里的百分数。

3. **Gold v1.1（下一份命名 split）**  
   - Evaluate：1003/1005–1008 改 planned 时态，或升级为 Log+Eval。  
   - Log/Comp：8205、5004、8301、8303 按上表修。  
   - 5005、9200 不动。  
   - 可选：`food_view` 暴露 `serving` 作为 qns 别名（catalog 观察，需 GPT 零漂移审查）。  
   - 经 `realize` / `compose_oracles` / freezer，禁止手改 JSON。

4. **不就地改 `v2.5-gold.json` / `nutrienv-gold.json`。** 若论文尚未引用这两个百分数，仍应出 **新 version 字段的新文件**，不要改已经跑出轨迹的那一份。

建议将本裁决固化为 ADR 0027（手册边界、唯一恢复性、Evaluate 时态、`amend_meal` 信封）。未写入 ADR 前，以上四条已是本轮终审意见。
