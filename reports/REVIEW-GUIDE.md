## 一、先说那个 ⚠️：多数情况它不是问题

> ⚠️ 无份量换算说明 (grams_explained 为空)

**它的意思**：这个克数，没法用任何一个「整齐的家用量具份数」解释出来。

生成逻辑在 `scripts/build_review_sheet.py:72`。它拿这条食物在 catalog 里的份量库（比如 `1 cup = 244g`）加上 oz、g，试着把克数除成一个整齐份数（1/4 步进到 8，外加 1/3、2/3、4/3、5/3），误差要 ≤0.005，还要反向验证一次。除不出来就留空，网页上就显示这行 ⚠️。

**所以它说的是「这个克数不是换算来的」，而不是「这个克数是错的」。** 绝大多数时候，原因就是用户在 query 里直接报了克数——`150g of chicken breast` 本来就不需要量具换算。

**看到它你该做的动作**：去上方 query 里找这个数字。

- **找得到** → 正常，这是「用户直接报克数」的题，可以 KEEP
- **找不到** → 克数凭空冒出来了，卡片顶部会同时亮红色 `unexplained_grams` 标签

**当前这 240 条的实际情况**：29 条会亮 ⚠️（共 36 行），全部落在 log(10) 和 evaluate(19)。而 `unexplained_grams` 风险标签是 **0 条**——也就是说，这 29 条的 query 里全都白纸黑字写了那个数字。基本可以快速放过。

### 份量的三种状态对照

| 网页上的显示 | 含义 | 要不要细看 |
|---|---|---|
| 🟢 `口语换算` + `1/2 x cup (244.0 g) = 122.0 g` | 单位在 query 里出现过（"半杯牛奶"） | 扫一眼即可 |
| 🟡 `推导等价` + 同样格式 | 除得开，但**这个单位 query 里没出现**，是系统自己挑的 | **要看，31 条** |
| ⚠️ 无换算说明 | 除不开任何整齐份数 | 去 query 里找数字，29 条 |

真正该盯的是**黄色的「推导等价」**：query 说「一根香蕉」，系统自己挑了 `1 x medium (118 g)` 来解释——单位是系统选的，就有选错的可能。这 31 条集中在 `v03-eval-*` 系列。

## 三、一张卡片从上往下怎么读

```
#12  v0-log-fuzzy-001  [log]  persona: everyday  fuzzy_portion     ← 身份
⚠️ spoken_portion  ⚠️ multi_candidate_food                          ← 风险标签
─────────────────────────────────────────────────────────────
"I had half a cup of milk with breakfast — can you log that?"     ← query：人说了什么
契约约束: The scorer compares the ledger tail to ...               ← 判分口径：机器会比什么
─────────────────────────────────────────────────────────────
S0 初始状态     过敏原 / 营养窗口 / 初始账本 / 起始 last_plan       ← 起点
期望终态        oracle 认定的正确终局                              ← 终点
窗口检查        计划营养总量 vs 窗口（仅 recommend 类）
档案变更对比    from → to 逐字段（仅 update 类）
─────────────────────────────────────────────────────────────
[1 保留] [2 需修改] [3 剔除]      意见框（自动保存）
```

读的顺序：**query → 契约约束 → 期望终态**。前两者告诉你「人要什么、机器比什么」，第三个是「机器认定的答案」。三者对不上，就是问题。

「期望终态」里每条食物会展开：`food_id`、完整 catalog 名称、克数与换算说明、该克数下的营养、过敏原标签，以及 **`other_candidates`（其他候选食物）**——这是判断选型对不对的关键材料。

## 四、五个家族分别审什么

| 家族 | 数量 | 判分依据 | 你要盯的 |
|---|---|---|---|
| **log** | 48 | 账本尾部精确匹配 | 口语份量换算成克数对不对；`other_candidates` 里为什么不是别的 |
| **recommend** | 72 | 非空计划 + 装进窗口 | 窗口**到底有没有解**（见下） |
| **evaluate** | 48 | last_plan 精确匹配 | 47 条有选型歧义——query 有没有把食物唯一钉死 |
| **update** | 36 | 整个 profile 对比 | 提到的字段改了吗、**没提到的字段是不是全停在 S0** |
| **constrain** | 36 | 安全响应 | 「允许空计划 / 计划必须安全」这套契约配得对不对 |

### 三处机器验不了、只能靠你

1. **108 条 recommend/constrain 的窗口检查全是 `total: null`**
   oracle 不固定具体食物行，脚本没东西可算。所以「这个窗口在 catalog 里到底配不配得出来」**完全没被验证过**，尤其那 17 条 `conflict_windows`。

2. **31 条「推导等价」份量**（见第一节）
   单位是系统自己挑的。

3. **56 条 `state_unpinned`（生熟状态未定）**
   食物名里带 raw / cooked，但 query 没说，而 catalog 里确实存在相反状态的条目。生米还是熟饭，克数差一倍。

## 六、判 KEEP / FIX / DROP 的标准

- **KEEP**——query 说的和 oracle 判的是同一件事，答案唯一且可从 query 推出来。
- **FIX**——**题的意图是好的，但细节写歪了**。比如选错了 `food_id`、克数换算错、update 动了 query 没提的字段、窗口配不出解。**在意见框写清楚该改成什么**，这是后续修题的唯一依据。
- **DROP**——题本身立不住。比如 query 有歧义、答案根本不唯一、或者和别的题重复。

拿不准的先跳过（`j`），最后用「待定」chip 筛出来集中处理。
